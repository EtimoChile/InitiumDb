| DEC-006 | ACTIVE | Prepare runs in autocommit; dataset in one transaction | `idb-prepare` is recovered by re-running it from the first step, so manual commit boundaries add nothing and make hook behavior depend on the engine (Oracle DDL commits implicitly). `preSql`/`postSql` run in autocommit as written. | DEC-007 | ACTIVE | SQL hooks are plain statements, no procedural blocks | A hook script is a sequence of SQL statements ending in `;`. InitiumDb does not parse or run procedural blocks (PL/SQL, `DO $$ ... $$`): that would make it a scripting runtime and tie hooks to each engine's procedural dialect. Hooks stay declarative; repeatability comes from idempotent statements (DEC-006). Conditional execution is a small notation over plain statements, not procedural code (DEC-010). | `README.md`, `core/SqlScript` | — |

| DEC-009 | ACTIVE | A case is a directory; file names are fixed by convention | `--case` names a directory whose name is the case name. It holds `case.yml` (`version`, ordered `databases: [{alias}]`) and, per alias, `<ALIAS>.queries.yml`, `<ALIAS>.dataset.xml` and the optional hooks `<ALIAS>.pre.sql` / `<ALIAS>.post.sql` (absent or empty run nothing). No path or boolean fields: `idb-init` always knows the files, never leaves orphans and can complete the files of an existing alias. Shared hooks and several hooks per alias are given up; two cases cannot share files (one directory each). Chosen over per-step path fields and over booleans for hooks. | `README.md`, `core/CaseConfig`, `core/ProjectInitializer`, `PrepareService`, `CaptureService` | Breaking: a case is a directory with fixed file names. |
| DEC-010 | ACTIVE | Conditional statements are `idb:` directives in line comments | Inside a hook, `-- idb:run-if <query>` or `-- idb:skip-if <query>` before a statement runs it only if the guard returns (run-if) or does not return (skip-if) a row; the guard is the rest of the line; one directive per statement, no nesting or `else`; the directive line is not sent to the database. Chosen over `@`-prefixed directives (`@file` means "run script" in SQL*Plus, and the file stops being plain SQL) and over case-level `runIf` fields (conditions belong per statement). The `.sql` stays valid SQL for other tools. Because a typo would silently run a non-idempotent statement, any `-- idb:` comment must be a valid directive, otherwise the run fails before any hook of the step runs. Other comments, including block comments, have no meaning and are kept as written. | `README.md`, `core/SqlScript`, `PrepareService`, `PrepareTest` | Add conditional SQL statements with `-- idb:run-if` and `-- idb:skip-if`. |
| DEC-011 | ACTIVE | Oracle and PostgreSQL apply the dataset with batched upserts | DBUnit 3.0.0 `REFRESH` costs 2 round trips per row (`SELECT COUNT(*)`, then `UPDATE` or `INSERT` as a batch of 1); measured 520 s vs 10 s on a 2265-row Oracle dataset. `DatabaseEngine.refreshOperation()` defaults to DBUnit `REFRESH`; `db/BatchedUpsertOperation` is the shared base (keys from the database metadata, no-PK table rejected, one upsert per row in JDBC batches of 500, LOB and engine-specific types fall back to DBUnit `REFRESH`); `OracleMergeOperation` writes `MERGE ... USING (SELECT ? ... FROM dual)` and `PostgresqlUpsertOperation` writes `INSERT ... ON CONFLICT (keys) DO UPDATE SET ... = EXCLUDED....` (`DO NOTHING` when every column is a key). Divergence: an absent attribute is written as NULL. `--refresh dbunit` forces the original. Still one transaction (DEC-006). | `README.md`, `db/BatchedUpsertOperation`, `db/oracle/OracleMergeOperation`, `db/postgresql/PostgresqlUpsertOperation`, tests | Apply the dataset with batched upserts on Oracle and PostgreSQL. |

| DEC-013 | ACTIVE | The dataset is read in two streaming passes against declared columns | DBUnit column sensing (`FlatXmlProducer(..., columnSensing=true)`) buffers each whole table to learn columns that appear after the first row, which does not scale and fails on large tables; it also cannot know a column that is NULL in every row (Flat XML omits NULLs). `idb-capture` writes every selected column to an internal DTD (`<!ATTLIST>`, bounded-memory copy after the XML declaration); `idb-prepare` first scans the file with a secure SAX parser (declared columns plus attributes seen, so old datasets still load; also rejects malformed XML before the pre hook), then produces rows with `FlatXmlProducer(source, metaDataSet)`. Memory is bounded by the number of columns. Proven by `PrepareMemoryTest` (60,000 rows, JVM limited to 40 MB; the previous approach does not finish). Refines the NULL divergence of DEC-011. | `core/DatasetColumns`, `CaptureService`, `PrepareService`, `PrepareMemoryTest`, `README.md` | Read datasets in constant memory and keep columns that are NULL in every row. |
| DEC-014 | ACTIVE | PostgreSQL uses `REFRESH` for tables whose dataset omits a NOT NULL column without default | `INSERT ... ON CONFLICT` validates NOT NULL on the proposed row before resolving the conflict (reproduced on postgres:17), so a partial capture (`SELECT col1, col2`) fails on rows that exist. `BatchedUpsertOperation.canUpsert` lets an engine veto the upsert per table; PostgreSQL vetoes when an omitted column is NOT NULL, has no default, is not auto-increment and not generated; the table then runs DBUnit `REFRESH` (updates only present columns). Oracle `MERGE` has no such check. Chosen over UPDATE-then-INSERT batches (more complex). | `db/BatchedUpsertOperation`, `db/postgresql/PostgresqlUpsertOperation`, `UpsertContractTest`, `PostgresqlRoundTripTest` | Fix partial datasets on PostgreSQL. |
| DEC-015 | ACTIVE | Timestamps without time zone are read and bound as `LocalDateTime` | DBUnit's `TIMESTAMP` type goes through `java.sql.Timestamp`, which interprets the value in the JVM's time zone, so a wall-clock time inside a daylight-saving gap of that zone was silently moved one hour on capture and prepare (reproduced on postgres:17 with `America/Santiago`, `2024-09-08 00:30`). Both engine profiles wrap their DBUnit type factory: a `TIMESTAMP` whose type name mentions no time zone (PostgreSQL `timestamp`, Oracle `DATE` and `TIMESTAMP`) uses `db/LocalTimestampDataType`, which reads with `getObject(LocalDateTime)`, binds with `setObject` and writes the same text as before (`yyyy-MM-dd HH:mm:ss.f`), so existing datasets stay valid and unchanged; other forms DBUnit accepts still load through DBUnit's parser. Types with a time zone (`timestamptz`, `TIMESTAMP WITH [LOCAL] TIME ZONE`) keep DBUnit's type, which preserves the instant. Chosen over forcing the JVM to UTC, which would also change the session time zone of SQL hooks. Part of PEND-011. | `db/LocalTimestampDataType`, `db/postgresql/PostgresqlEngine`, `db/oracle/OracleEngine`, `DatasetTypesTest`, `integration/*TypeRoundTripTest`, `README.md` | Fix: timestamps without time zone no longer shift by an hour when they fall in a daylight-saving gap of the machine's time zone. |
| DEC-016 | ACTIVE | Capture rejects text that XML 1.0 cannot hold, and writes characters outside the BMP as one reference | XML 1.0 forbids most control characters (below U+0020 except tab, LF, CR; U+FFFE, U+FFFF) even as character references; DBUnit's `XmlWriter` wrote them raw, so capture produced a dataset that `idb-prepare` could not read. `CaptureService` now checks each text value against the XML `Char` production and fails naming table, column, row and code point, never the value (it may be personal data); the previous dataset is kept. Chosen over encoding them (like PEND-006 for names), which would need a private escape convention in every value; tracked as PEND-018. The same `XmlWriter` escapes each UTF-16 unit separately, so an emoji became two references to surrogates (`&#55357;&#56832;`), also invalid; `core/SurrogatePairWriter` joins each pair into one reference (`&#128512;`) as the file is written. Part of PEND-011. | `CaptureService`, `core/SurrogatePairWriter`, `DatasetTypesTest`, `integration/*TypeRoundTripTest`, `README.md` | Fix: text with emoji or other characters outside the Basic Multilingual Plane is captured correctly; text with forbidden control characters now fails the capture with the table, column and row instead of writing a dataset that cannot be prepared. |
| DEC-017 | ACTIVE | Datasets may not declare entities; the JDK's entity size limits are lifted | The JDK's XML parser counts each predefined reference (`&amp;`, `&lt;`, `&quot;`, ...) against `jdk.xml.maxGeneralEntitySizeLimit` (100,000 on JDK 25), so `idb-prepare` failed with `JAXP00010003` on a value with that many escaped characters (a large JSON or XML text, a `CLOB`), although capture had written it correctly (reproduced on H2 and Oracle). Those limits exist against expanding declared entities, so the structure scan (`DatasetColumns.scan`, which runs before the pre hook and before DBUnit's parser) now rejects any `<!ENTITY>` declaration, and `jdk.xml.maxGeneralEntitySizeLimit` and `jdk.xml.totalEntitySizeLimit` are set to 0 as system properties, the only way to reach the parser DBUnit's `FlatXmlProducer` creates. Limits on the number of expansions keep their configured values. Part of PEND-011. | `core/DatasetColumns`, `DatasetTypesTest`, `integration/oracle/OracleTypeRoundTripTest`, `README.md` | Fix: `idb-prepare` no longer fails on large text values full of characters such as `&`, `<` or `"`; a dataset that declares XML entities is now rejected. |
| DEC-018 | ACTIVE | Floating point, PostgreSQL `numeric`, Oracle `FLOAT` and PostgreSQL types DBUnit does not know get their own data types | DBUnit parses `DOUBLE`/`REAL` dataset text through `BigDecimal`, so `NaN` and the infinities failed (`TypeCastException`) and `-0.0` became `0`; Oracle's driver converts `setDouble` to `NUMBER`, so `BINARY_DOUBLE` values past 1E126 failed with an unchecked `IllegalArgumentException: Overflow`; Oracle `FLOAT(126)` was read as a `double` (15 digits); PostgreSQL `numeric` `NaN` could not be read; and DBUnit maps `json`, arrays, `interval`, `inet` to `UNKNOWN` (the column was dropped, `NoSuchColumnException` on prepare) and binds enums as `varchar` (42804). Now `db/FloatingPointDataType` parses with `Double`/`Float` and binds `BINARY_DOUBLE`/`BINARY_FLOAT` with `setObject(.., 101/100)` (no compile-time ojdbc dependency); Oracle `FLOAT` uses DBUnit's `NUMERIC`; PostgreSQL `numeric` keeps `NaN`/`Infinity` as text (`postgresql/NumericDataType`); PostgreSQL `UNKNOWN`, `ARRAY` and enum columns (a `VARCHAR` whose type name is not a character type) are read with `getString` and bound as `Types.OTHER` so the server casts them (`postgresql/TextCastDataType`, kept on the batched upsert through `BatchedUpsertOperation.isBatchable`). Any unchecked exception while applying now ends as the alias error instead of a stack trace. Part of PEND-011. | `db/FloatingPointDataType`, `db/postgresql/{NumericDataType,TextCastDataType,PostgresqlEngine,PostgresqlUpsertOperation}`, `db/oracle/OracleEngine`, `db/BatchedUpsertOperation`, `core/PrepareService`, `DatasetTypesTest`, `integration/*TypeRoundTripTest`, `README.md` | Fix: `NaN`, infinities and `-0.0` round-trip; Oracle `BINARY_DOUBLE` accepts its whole range and `FLOAT` keeps all its digits; PostgreSQL `json`, `jsonb`, arrays, enums, `interval`, `inet` and `cidr` columns are captured and applied. |
